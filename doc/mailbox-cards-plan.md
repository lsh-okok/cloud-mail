# 邮箱卡密管理与兑换方案

日期：2026-11-16

状态：业务基线已确认，已完成当前工作区实现与本地验证；实现与验证见 [mailbox-cards-implementation.md](mailbox-cards-implementation.md)。未部署。

本聊天职责：邮箱兑换码管理、一次性核销、TXT/ZIP 交付和兑换订单查询。

## 1. 已确认的业务规则

1. 一个兑换码固定绑定一个主邮箱，不能换绑。
2. 每个码只能成功核销一次；失败不消费该码。
3. 管理员可以手动停用，也可以重新生成新码。未核销、已停用及已核销的当前码均可重新生成；新码仍绑定原主邮箱，旧码永久作废。
4. 兑换交付该主邮箱下所有子邮箱，TXT 每行内容严格为 `子邮箱----子邮箱取码链接`。
5. 单码兑换交付一个 TXT；批量兑换按一个主邮箱一个 TXT 分文件，并压缩为 ZIP 交付。
6. 已交付的原链接继续使用，以原链接有效期及现有取信策略为准；重新生成或核销新码不重置原链接有效期。
7. 提供查询订单接口，用于查看本次兑换记录和重新下载交付结果。
8. 兑换码默认长期有效，与子邮箱链接的有效期独立。

用户已进一步澄清：“可以重复使用”是指已核销后可生成新码，原链接继续有效；同一个兑换码仍然只核销一次。

用户已于 2026-11-16 授权开始开发。下文为实现基线，常规实现细节不再视为新的业务阻塞项。

## 2. 当前实现与范围

项目原有 MX/本地来源、主邮箱、子邮箱链接、平台规则、匿名取信及主从节点；本次在此基础上新增邮箱兑换码、核销订单及文件交付模块。邮箱来源沿用现有本地/MX 支持范围，不增加 Outlook/iCloud 接入；注册邀请密钥与本模块不同。

历史需求 [feature-migration-requirements.md](feature-migration-requirements.md) 第 5 节曾规定外部邮箱及重复找回当前链接，旧技术方案因仅支持 MX 而将卡密排除。本方案中的用户最新规则优先于历史规则；历史原件保留，现行技术方案和开发拆分已增补本地卡密范围。

兑换绑定现有 `source_mailbox.id`。单账号模式和受控域名模式均复用既有来源可读性检查，子邮箱集合只取明确关联该主邮箱 ID 的链接记录；不能把同域名的其他主邮箱或所有邮件地址自动纳入。

本模块中的订单指兑换订单，记录一次请求的逐码结果和交付文件，不引入支付、退款、客户账号或外部商城订单模型。

## 3. 交付内容与文件规则

### 3.1 全部子邮箱与链接

- 成功核销时快照该主邮箱下现有全部子邮箱链接，交付完整地址和精确取码 URL；不包含邮箱登录密码、邮件正文或其他凭据。
- 同一子邮箱存在多个平台链接时，每个不同链接各占一行，不能擅自合并成更宽权限的链接。按完整子邮箱、平台 ID、链接 ID 固定排序，仅对完全相同的地址与 URL 组合去重。
- “全部”不能实现为静默截断或只取第一页。已存在但已经到期的链接仍纳入原样交付，页面与订单元数据展示到期情况；下载和重新生成兑换码均不延长期限，过期链接打开时仍按原规则拒绝。
- 来源、关联账号及用户必须符合现有可读条件；主邮箱没有任何子邮箱链接时该码失败，不核销。
- 若某条记录因平台失效、数据异常或 Token 无法解密而不能生成准确的原链接，该主邮箱交付失败，不省略该子邮箱后声称全部成功。可确定的配置问题返回逐码原因；数据库、密钥服务等内部故障按整批回滚处理。
- 本模块不根据邮箱前缀猜测子邮箱，也不自动创建不存在的链接。若未来增加独立子邮箱目录，目录中的无链接项也必须显式处理，不能漏交付。
- 交付完成后形成固定快照。订单查询和重新下载都使用该次快照，不加入后来新增的子邮箱或替换后的 URL；原链接的后续使用仍受实时取信策略约束。

### 3.2 TXT 与 ZIP

TXT 使用 UTF-8 BOM 和 CRLF，每行严格为：

```text
child@example.com----https://mail.example.com/m/exact-token
```

文件正文不加表头、主邮箱汇总、兑换码、订单密钥、失败说明或平台标签。平台和到期信息放在订单页面与元数据中；不改变用户规定的两列格式。

- 单码请求：生成对应主邮箱的一个 `.txt`。
- 批量请求：每个成功主邮箱一个 `.txt`，统一放入一个 `.zip`；批量按原始卡密数量校验并去重后的数量大于 1 判定。即使只有一个主邮箱成功，也保持 ZIP 交付。
- 失败码不生成空 TXT，失败原因在订单逐项结果中显示；全部失败时订单无下载文件，不消耗任何码。
- 同一订单中的同一主邮箱只形成一个文件；历史已作废或已核销码不能形成额外重复交付。
- 文件名建议为安全化主邮箱地址加短来源 ID，ZIP 外层名包含订单号。过滤目录分隔符、控制字符、Windows 保留名、尾部点/空格，限制长度并处理重名，ZIP 条目不能包含目录穿越路径。
- 保存生成时的文件名、格式、内容摘要和大小；重复下载保持当次文件内容，不用当前邮箱名称重新命名，也不实时重建业务集合。

交付文件、ZIP 和文件元数据必须在核销事务提交前完整生成并通过容量检查。下载失败可通过订单再次获取，不能以“下载未完成”为由重置核销状态。

## 4. 管理与公开流程

### 4.1 管理页 `/admin/cards`

以符合支持范围的主邮箱为行，未生成码的主邮箱也显示。默认每页 50，可选 20/50/100；切换搜索、状态、页码、页容量及刷新后清空选择。

字段包含主邮箱、主邮箱状态、子邮箱数量、链接数量、当前兑换码、码状态、生成时间、核销时间和历史入口。子邮箱数按完整地址去重，链接数按链接记录计数；两者不标成当前仍可使用的链接数量。

操作包含初次生成、复制、手动停用、重新生成、历史记录及订单查看。建议允许恢复未核销且未作废的当前停用码；恢复不清除核销或作废终态。

当前码统计分为未生成、未核销、已核销、已停用。核销优先于停用，停用优先于未核销，确保一个主邮箱只计入一个当前状态；作废码显示在历史中并保留此前核销事实。全局统计不随当前搜索变化。

按主邮箱模糊查询、完整码精确查询；完整码只能放受保护 POST 请求体，不能进入查询参数。首版批量操作限当前页明确勾选，不包含跨页全选。管理员码 TXT 每行一个当前未核销且启用的码；历史码不混入待发码导出。

初次生成一次接受 1～500 个主邮箱 ID，先验证原始数组大小和类型，再去重。目标须存在且通过来源/账号/用户检查，可以暂时没有链接。整批原子提交，任一目标不合法则整批不新增；已有当前码时返回原记录，不重置核销或自动换码。

重新生成独立于初次生成：携带目标码 ID、版本及管理员操作幂等键。旧码作废、新码创建、当前指针切换、替换关系及审计同事务提交；新码默认未核销、启用、长期有效。已核销后的重新生成表示为同一主邮箱重新授权一次交付，旧订单与原链接不变。同一次管理操作重试返回同一新码，不能连续换出多代。

### 4.2 公开兑换页 `/redeem`

1. 无需登录，支持粘贴或追加单个 TXT 文件，文件导入不自动提交。
2. 支持换行、空格、中英文逗号和分号，保留码的大小写并按原顺序去重，实时展示数量。
3. 一批最多 100 个码，客户端 TXT 上限 256 KiB；提交前生成高熵请求/查询凭证，供用户保存。提交期间禁止重复操作。
4. 提交成功后显示订单号、逐码结果、成功主邮箱数、子邮箱数、链接数、文件格式和下载入口；单码 TXT、批量 ZIP。
5. 新请求提交已核销、已停用或已作废码时，分别返回对应原因。同次请求超时则携原凭证和内容重试；明确失败的码另用新凭证形成新订单，不重新提交已成功码。
6. 页面可保留之前订单的成功信息，但每个下载入口明确对应自己的订单，不将不同订单的文件混成一份未记录的交付结果。

客户端不自动将兑换码、交付内容或查询凭证写入 localStorage、URL、历史记录或埋点。提供复制/下载订单查询凭证的显式操作，并在提交前提示保存凭证；用户关闭页面后仍可凭保存的凭证查询。

### 4.3 订单查询与重复下载

一次提交形成一个兑换订单，包含逐码成功/失败结果，每个成功项关联一个主邮箱及固定交付文件。批次可为成功、部分成功或全部失败；失败项不核销。

订单查询授权建议采用“订单号＋高熵查询凭证”。查询凭证由客户端提交前生成，至少 32 字节随机值，可作为该次 `requestKey` 使用，但必须明确其同时具备读取交付结果的权限；不使用兑换码或主邮箱作为查询密钥。订单号只是标识，单独提供时不授权访问。

查询 API 的请求体必须提供查询凭证，订单号可选：正常查询使用两者；首次兑换响应丢失、尚未拿到订单号时，可凭提交前保存的查询凭证定位原订单。若同时提供订单号，必须与凭证对应。管理员可经现有管理员认证查看订单，匿名持有人不能列举订单或按邮箱查单。

订单查询返回原兑换时间、状态、逐项结果、主邮箱及文件元数据，下载接口返回当次 TXT/ZIP。查询与下载不再次核销、不重新枚举当前链接、不包含未提交的码或其他订单。

重新生成、停用兑换码不会删除已成立订单；原订单仍可凭原查询凭证下载，文件中的链接继续按原有效期和当前取信策略使用。泄漏兑换码和泄漏订单查询凭证是两种访问问题：更换兑换码只阻断旧码的新兑换；需要阻断已泄漏链接的读取时，按链接/主邮箱策略处理。

订单快照与短期请求缓存分离，不沿用先前草案的“24 小时后无法找回”规则。建议首版长期保留订单、查询凭证摘要和加密交付内容，容量不足时先拒绝新兑换，不自动删除尚未约定可清理的交付记录。未来如配置保留期，需在订单中明确展示；结果清理不抹除永久核销或作废事实。兑换码默认长期有效不代表任何已到期链接被续期。

## 5. 一次性核销、历史与并发

核销以服务端事务成功提交为准，不能根据用户点击、HTTP 超时或收到半段文件判定。一个码最多一条成功核销记录，订单快照与核销必须同事务成立。

- 同一请求凭证、相同规范化内容：仅执行一次核销，其后返回同一订单；不同内容复用同一凭证返回 409。
- 两个不同请求凭证争用同一码：最多一个成功，另一个返回已核销；持已核销码不能借新查询凭证找回原订单。
- 重新生成或停用先提交：旧码不能再核销；旧码核销先提交：原次交付有效，后续换码可创建新码，原订单仍保留。
- 来源删除后关联码全部失效，建议保留绑定快照、核销/作废历史及审计，解除实时外键关联；同地址重建邮箱不继承旧码或旧订单的写权限。
- 固定绑定来源 ID 与发码时账号身份。建议有兑换码时禁止换成另一账号、修改主邮箱地址或改变收件模式；也须在核销时检查，防止其他写入路径将旧码转交给新邮箱。
- 普通来源设置更新可能增加现有 `generation`，不能直接将它作为永久身份绑定，否则停用再恢复会误使原码失效。

逐码业务失败可与同批成功并存。数据库、密钥服务、ZIP 生成、序列化或内部组装故障导致整批回滚，不留下已核销但无订单文件的状态。配置错误导致某主邮箱不能完整交付时，该码失败，不静默缩小“全部子邮箱”的范围。

候选执行顺序：校验请求和凭证→进入 SQLite immediate 事务并查重请求、核对请求指纹→已有完成订单则返回原订单→复核各码和来源→构建全部 TXT、批量 ZIP、加密内容及元数据→检查容量→条件核销成功项→持久化订单、逐项结果和审计→提交。所有生成过程必须有界，不在数据库事务内执行外部网络请求或健康检测。

请求查重在事务内进行，以请求凭证摘要唯一约束兜底。核销条件包含当前、启用、未作废、未核销及身份未变，并以核销记录的 `card_id` 唯一约束兜底。事务后发送下载失败不回滚核销，由订单重复下载补偿。

## 6. 候选接口与数据模型

接口前缀 `/api` 沿用当前服务约定。

| 方法与路径 | 作用与关键约束 |
| --- | --- |
| `GET /api/admin/cards` | 主邮箱分页、码状态和全局统计；禁止完整码查询参数 |
| `POST /api/admin/cards/search` | 完整码精确搜索，管理员认证及 CSRF |
| `POST /api/admin/cards` | 按 `mailboxIds` 原子初次生成，已有当前码不重新授权 |
| `PUT /api/admin/cards/{cardId}` | `enabled` 布尔值及版本，手动停用/恢复；不清除核销/作废状态 |
| `POST /api/admin/cards/{cardId}/regenerate` | 版本＋管理操作幂等键，原子换码；允许已核销后生成新码 |
| `GET /api/admin/cards/{mailboxId}/history` | 各代兑换码与替换、核销、停用和作废历史 |
| `POST /api/admin/cards/export` | 按明确勾选 ID 导出当前未核销且启用的码，最多 500 个目标 |
| `GET /api/admin/cards/config` | 公开兑换页地址，复用公开根地址与部署前缀 |
| `GET /api/admin/redemption-orders` | 管理员订单列表，按订单号/主邮箱/状态筛选，不使用匿名查询凭证搜索 |
| `GET /api/admin/redemption-orders/{orderNo}` | 管理员查看订单与文件元数据 |
| `POST /api/admin/redemption-orders/{orderNo}/download` | 管理员下载该订单原 TXT/ZIP，审计下载动作 |
| `POST /api/redeem` | `{ "codes": [...], "requestKey": "..." }`，核销并返回订单信息；同请求重试返回同订单 |
| `POST /api/orders/query` | `{ "orderNo": "可选", "queryKey": "必填" }`，查本次兑换订单；凭证错误返回统一不可查询结果 |
| `POST /api/orders/download` | 同查询授权正文，返回原 TXT/ZIP；不把凭证放入 URL |

匿名接口只在主节点提供，查询和下载均适用来源校验、不可缓存及限流。订单与下载返回真实 HTTP 状态，不用成功状态包装未授权或内部错误。

候选持久模型：

| 表 | 关键内容与约束 |
| --- | --- |
| `mailbox_card` | `id`、`mailbox_id`、唯一 `code_digest`、`code_encrypted`、`is_current`、`enabled`、`revision`、`created_at`、`redeemed_at`、`revoked_at`、`supersedes_card_id`、绑定账号/邮箱及操作者；码本身默认无到期限制 |
| `card_redemption` | 唯一 `card_id`、主邮箱绑定快照、核销时间及订单项 ID；一张码最多成功一次 |
| `redemption_order` | 随机订单号、分别唯一的 `request_key_digest` 和 `query_key_digest`、请求内容摘要、单码/批量模式、结果状态、创建时间、文件元数据及加密交付包；凭证原值不持久化 |
| `redemption_order_item` | 订单 ID、输入序号、码记录引用、逐项结果、主邮箱/子邮箱/链接加密快照、TXT 文件名与加密内容；不将原始码明文放入普通持久结果 |
| 管理操作幂等记录 | 管理员身份、操作键摘要、目标码/版本、内容指纹及新码引用；与匿名订单用途隔离 |

一个主邮箱可保留多代兑换码，`mailbox_id` 不能全表唯一；用局部唯一索引保证每主邮箱最多一个当前码。仅当前、启用、未核销、未作废的码可兑换。当前码被替换后，保留此前已核销事实和作废记录。

若码表保留冗余 `redeemed_at`，必须和唯一核销记录同事务写入并保持一致。主邮箱删除时保留不可变绑定标识和快照，不因外键级联丢失历史；订单成功项与文件内容不得后续覆盖为当前状态。

兑换码建议为 `ML-` 加 32 字节随机值的 base64url 编码，以原大小写计算 SHA-256 摘要；高熵随机码摘要不依赖加密密钥轮换。密文复用 SecretVault 的 AES-256-GCM，码与订单内容使用独立 AAD，例如 `mailbox-card:{id}`、`redemption-order:{id}`。旧解密密钥须随保留数据可用。

匿名查询凭证建议复用该次高熵 `requestKey`，同一原值分别计算请求用途与查询用途的独立摘要，持久化到 `request_key_digest` 和 `query_key_digest`，各自建立唯一约束并按用途查找。公开请求响应不回传其他记录的凭证或完整码。重新下载只需要订单授权，不需要再次提交旧兑换码。

订单项中包含完整 URL/Token 的链接快照同样必须放入加密载荷，不能只加密 TXT/ZIP 而将等价快照另存为明文 JSON。

新增有序迁移，不修改已发布的历史迁移；实施时按仓库最新顺序分配版本。唯一约束、版本条件和 immediate 事务共同保证初次发码、重新生成、核销及订单幂等一致。

## 7. 校验、容量与现有接入点

公开 JSON 请求体沿用 64 KiB 实际字节上限。原始 `codes` 为 1～100 项，先验证再去重；每项修剪外围空白后按 UTF-8 不超过 128 字节。请求/查询凭证严格校验长度和编码，订单指纹包含规范化卡密顺序、批量模式及其他业务字段。拒绝非法 JSON、类型错误、未知字段和尾随内容。

候选容量：每码 1000 条链接、每批 5000 条链接、交付文件未压缩合计 8 MiB，并另外限制 ZIP 字节数、加密快照大小和下载并发。这些值待实现压测；超限须在核销前明确失败，不截断“全部子邮箱”，也不只依赖压缩后较小的体积放行。

| 接入点 | 复用方式与必要补齐 |
| --- | --- |
| `mail-worker/src/modules/router.js` | 新增独立 cards/orders 服务，保持 `/admin/*` 授权边界 |
| `modules/shared/security.js` | 管理端复用 `requireAdmin`；提取现有私有来源校验，显式用于匿名兑换、查询及下载 |
| `modules/shared/errors.js` | 复用 `strictJson` 字节、UTF-8、JSON 和未知字段校验，增加码、凭证、订单及版本约束 |
| `modules/mail-sources/service.js` | 复用 `assertSourceReadable` 和完整子邮箱归属规则，增加固定身份及编辑约束 |
| `modules/public-mail/service.js` | 复用取信规则；需调整无差别 catch，保留未知内部故障。交付快照可纳入过期 URL，不调用会过滤过期项的完整读取校验来静默缩小集合 |
| `modules/links/service.js`、`shared/urls.js` | 复用 `linkDto` 和 `publicUrl`，补齐 JOIN 字段；短 URL 必须精确解析到原收件人/平台，歧义回退 Token URL |
| `modules/shared/secrets.js`、`settings.js` | 复用加解密、密钥版本和 `appendAudit`；核销、换码、订单及文件下载审计只记录 ID、动作、数量、结果 |
| `server/kv.js`、`shared/proxy.js` | 基于持久原子计数和可信 `clientIp` 新增兑换/查询/下载限流；现有代码没有可直接挂载的兑换限流器 |
| `server/app.js`、`modules/nodes` | 明确兑换页安全头与路由；子节点拒绝订单接口，检查同步/快照不含码、订单或查询凭证 |
| `mail-vue/src/perm/perm.js`、`router/index.js` | 增加管理页、公开兑换和订单查询页，公开路由放行登录守卫，菜单与国际化同步 |
| `mail-vue/src/request/features.js` | 复用管理/匿名客户端分离，补充 POST TXT/ZIP 完整下载校验、查询和同次请求重试 |
| `modules/cards/delivery.js` | 基于 Node.js 24 内置 DEFLATE/CRC32 生成有界 ZIP32，包含 UTF-8 条目、安全文件名、稳定顺序和完整性校验，无新增依赖 |

建议同一可信 IP 的兑换请求每固定 60 秒最多 30 次；查询、下载设置独立额度与带宽/并发限制。超限返回 429 和 `Retry-After`，非法凭证尝试也计入。客户端来源只能用服务器解析的 `clientIp`，不能自行信任转发头；此策略只承诺现有单可写主节点。

兑换码、查询凭证、取信 Token、TXT/ZIP 正文和完整交付 URL 不进入普通日志、审计字段或埋点，不放 URL。所有相关 API、文件与公开页面不可缓存，页面拒绝第三方嵌入；匿名提交、查询、下载拒绝跨站浏览器请求，不能放开任意 CORS。

下载响应设置正确的 TXT/ZIP 类型、附件文件名、内容长度和 SHA-256 校验。客户端完整接收并验证后保存，失败不保存半份文件；文件 URL 不公开为无凭证静态路径，也不转交给无订单数据的只读节点。

码、订单及加密交付结果不进入 `sync_event`、节点配置或快照/增量 DTO。主节点备份覆盖新增表，数据密钥独立保存；恢复验证覆盖核销状态、换码历史、订单文件、查询授权和旧密钥。恢复旧备份可能遗漏后续核销，需先冻结兑换并对账，不能将回退后的未核销标志直接作为可用依据。

## 8. 实施顺序与验收出口

| 阶段 | 产物 | 验收重点 |
| --- | --- | --- |
| 范围同步 | 更新当前技术方案、开发拆分与接口契约 | 最新业务基线明确，历史重复兑换规则不混入 |
| 码管理基础 | 多代历史、密文/摘要、初次生成、停用、重新生成、搜索与导出 | 已核销后可换新码；旧码永不再用；同操作重试不多换；当前码唯一 |
| 核销与订单 | 一次性核销、订单与逐项快照、查询凭证、并发控制 | 不同请求争码只有一次成功；同请求返回同订单；文件生成或保存失败不核销 |
| 文件交付 | 单码 TXT、批量每主邮箱一 TXT 的 ZIP、下载校验 | 两列格式准确；全部子邮箱不漏项；多平台不扩权；文件不混主邮箱；命名安全且不覆盖 |
| 页面与查询 | 管理/公开兑换/查单、保存查询凭证、重新下载和失败重试 | 单独订单号或旧码不能查交付；首次响应丢失可凭预存凭证查单；下载原文件不再核销 |
| 联合验收 | 权限、来源生命周期、节点、前缀、容量和恢复 | 换码/停用与兑换竞争一致；过期 URL 不续期；旧订单不随新码改变；子节点无凭证或订单数据 |

补充场景：

- 单码成功下载一个 TXT；两个码成功下载两个 TXT 的 ZIP；批量仅一项成功仍下载一个 TXT 的 ZIP；全部失败无空文件且所有码未消费。
- 已核销码不能新建成功兑换；生成新码后可再核销一次，旧交付链接仍按原有效期使用。
- 订单查询与重复下载返回原文件，不加入新子邮箱、延长期限或重置核销；过期链接仍在当次文件中且按原规则过期。
- 同一子邮箱不同平台多行交付，同域名/同本地部分不串链接；主邮箱没有链接或某条无法准确交付时明确失败，不假成功。
- 同键不同内容冲突；错误查询凭证不暴露订单是否存在；仅持旧兑换码不能枚举订单。
- 密钥缺失、数据库异常、ZIP 失败或磁盘/容量不足均不留下无文件的成功核销；下载中断可重试原订单。
- 来源删除重建不继承旧码，保留历史订单；备份恢复不错误恢复已核销码的可用性。

实现范围包含数据库迁移、接口、管理/公开页面、TXT/ZIP 和回归测试；部署另行执行，验证证据见实现说明。
