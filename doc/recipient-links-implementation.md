# 主邮箱与子邮箱收件链接：第一批实现

日期：2026-11-13  
关联：[需求基线](feature-migration-requirements.md)、[技术方案](feature-migration-technical-plan.md)、[开发拆分](feature-migration-development-breakdown.md)

范围更新：本批交付 MX/本地收信与子邮箱独立链接，也支持 iCloud 等跨域子地址已转发到本站主邮箱的场景；不新增 Outlook/iCloud 取信对接。此范围优先于保留的原始需求副本。外部邮箱协议、授权、凭据导入及真实外部邮箱联调不纳入交付。

## 业务关系

主邮箱 A 是本地实际收信来源，a1、a2、a3 是已经能接收邮件至 A 的完整收件地址。系统为每个子地址生成独立页面/JSON 链接；链接只允许查看该地址与平台策略匹配的邮件。子地址不创建 Cloud Mail 登录用户，不需要分别配置登录凭据。

例如 A 中同时存在发给 `a1@example.com`、`a2@example.com`、`a3@example.com` 的邮件，打开 a1 的链接只显示 a1 的结果。邮件是否属于子邮箱取决于实际收件证据，不能靠正文包含地址、显示名称或模糊匹配判断。链接生成不负责在邮箱服务商创建别名或设置转发。

## 使用方法

1. 在服务器环境设置独立 `DATA_ENCRYPTION_KEY`：64位十六进制随机值，与 JWT_SECRET 分开；保存到受保护的恢复材料。示例文件仅提供空配置，不会替已有服务器生成或修改密钥。
2. 登录管理员，打开“主邮箱管理”，选择现有本地账号，或明确选择整个受控收件域名；两种范围分别对应单账号与域内已存储邮件。保存只验证配置，不会自动发信。
3. 进入该主邮箱的“管理子邮箱链接”，填写完整子地址，一批最多10000个，可选平台与到期时间；生成后复制每个地址的页面或JSON链接。
4. 各链接无需登录；默认页面显示最新一封，可切最近邮件和排序。无匹配邮件正常显示空结果，上游故障有独立错误/重试。

导入 TXT 时可勾选“TXT 首行为主邮箱”（默认不勾选）。勾选后，每个文件第一行填写一个完整主邮箱地址，其余行填写完整子邮箱地址，允许子地址与主邮箱不同域，例如本站主邮箱下的 iCloud 转发地址；系统精确匹配已有主邮箱，不存在则创建当前管理员的本地邮箱及主邮箱配置，并自动选中。首行不加入子邮箱名单，仍需点击“生成链接”完成子邮箱链接创建。已有主邮箱的配置和链接保持原样，停用的主邮箱会提示错误。多个文件须使用同一个主邮箱，子地址完整性及去重后 1～10000 个的限制仍有效；如表单已有其他主邮箱的子地址，先清空名单再导入。不勾选时，所有行继续按原方式追加为子邮箱地址。

MX 账号范围读取该账号收到的邮件：本地子地址按完整信封地址匹配；iCloud 等跨域子地址已转发到该主邮箱时，可按邮件保留的原始 To/Cc 完整地址精确识别。跨域匹配始终限定在所选主邮箱的邮件内，不跨主邮箱搜索，也不会把主邮箱全部邮件交付给子地址。域名范围可读取该受控域名已存储的对应收件地址。转发邮件若缺失原始 To/Cc，或原始子地址仅在 Bcc 中，无法识别该跨域子地址；系统不会根据正文、显示名称或其他转发头猜测归属。

取信服务设置在主邮箱管理页提供；公开根地址可含路径，系统时区默认为 Asia/Shanghai。修改设置需要已加载的 revision，防止旧表单覆盖新值。

## 部署配置

- `DATA_ENCRYPTION_KEY`、`DATA_ENCRYPTION_KEY_ID`：保护链接 Token 的当前认证加密密钥及版本，默认ID为v1。未配置密钥时旧邮箱功能可运行，链接生成返回明确503。
- `DATA_ENCRYPTION_PREVIOUS_KEYS`：旧版本密钥的JSON映射，允许读取旧密文；本批未提供自动重加密CLI。
- `PUBLIC_BASE_URL`：可选公开链接根地址，HTTPS，可带部署前缀；管理设置中的公开根地址优先。
- `APP_BASE_PATH`：例如 `/mail`；前端构建与后端运行使用相同值，NPM代理保留该前缀，修改后需重建镜像。
- `TRUSTED_PROXIES`：明确可信代理IP/CIDR列表；为空时不信任任何转发头。应配置NPM实际来源范围，不将任意公网地址设为可信。
- 开发使用Vite代理时，`APP_URL`的Origin需与实际打开的前端站点一致，管理写校验不会因为开发模式放宽。

数据库迁移版本3提供本地来源、平台、链接与 Token 保护、设置、事件及审计所需结构。为兼容已有数据库，保留历史 provider 枚举及 `source_secret` 表；运行时仅支持 MX，历史外部来源与链接保留但不展示、不读取。迁移通过现有框架原子应用，不改注册邀请密钥或旧登录用户的业务含义。

## 验证与边界

### 2026-11-14：跨域转发子邮箱

支持 iCloud 等外域子地址已在上游转发至本站主邮箱的场景。子链接创建及“TXT 首行为主邮箱”导入不再要求子地址同域；本站主邮箱本身仍须属于已配置的本地收信域名。读取外域子地址时，先限定实际 SMTP 信封等于所选主邮箱完整地址，再精确匹配原始 To/Cc；账号型来源另校验存储账号。整域来源也不会扫描其他主邮箱来匹配外域子地址。本地域子地址继续使用精确信封规则。已有邮件保存的原始收件人信息可以直接使用，无需迁移。

- 全量回归：24 个测试文件、290 项通过；随后新增的真实主节点→副本转发读取测试单独 1 项通过，合计验证 291 项。
- 新增转发专项 8 项覆盖真实入站解析、To/Cc、组地址、同名前缀不同域、历史邮件、坏 JSON、主邮箱/plus 隔离、已发送邮件排除及本地域规则；TXT 专项 27 项通过。
- 主副节点联调回归验证原始 To/Cc 和真实信封透传、副本二次匹配、不同主邮箱隔离，以及主源停用后缓存即时拒读。
- 前后端生产构建通过。本机隔离预览通过网页一次生成 750 个 `@icloud.com` 测试链接，并分别打开两个转发子邮箱页面，确认各自显示对应邮件。
- 本机截图：`data/forwarded-recipients-750-success.jpg`、`data/forwarded-recipients-read.jpg`（忽略的测试资料目录）。本次使用模拟转发邮件，未连接真实 iCloud 账号或修改已部署的服务器；主节点和副本均需更新本次版本才能使用新匹配规则。

外域 To/Cc 是主邮箱内的分类依据，不能证明邮件确实由 iCloud 转发。原始 To/Cc 被上游改写丢失、或子地址只存在于 Bcc 时不会猜测归属，也不会放宽为读取整个主邮箱。

自动化使用临时数据库与本地邮件样本，覆盖a1/a2/a3隔离、plus、平台/期限、非法批次、来源撤销竞争、旧游标、缓存、可信代理及路径前缀。浏览器已检查公开a1/a2页面、管理员列表、390像素卡片与生成表单；根路径与 `/mail` 前缀前端构建均成功。
